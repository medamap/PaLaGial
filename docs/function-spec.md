# 機能仕様（規格） v0.1 ドラフト

タマゴはスクリプトを固定しない。エージェントシステムごとに実装表記が違うためである。
代わりに本書が **機能の一覧・各機能の処理概要・入出力** を規格化する。
インストールしたエージェントは、本書の入出力を満たす実装を自分の環境の流儀で生成する。

表記： 入力／出力は論理的なデータであり、ファイル形式は YAML を推奨する（YAML→JSON の片方向生成は可）。

---

## F1. bootstrap（全ランの入口）

- 概要： すべての定常ランと作業開始時に最初に実行する。稼働状態を読み、現行版を確定し、対象プロジェクトの定義とアクセス固定を解決してから、プロジェクト固有の入口へ渡す。bootstrap 自体は個別の作業内容を定義しない。
- 入力： `~/.palagial/config.yaml`（アンカー。唯一のハードコード地点。data/schemas.md §0）、`SPEC/status.yaml`、`SPEC/current_version.yaml`、現行版フォルダ一式、対象プロジェクト slug、`SPEC/runtime/` の状態。
- 処理：
  0. アンカーを読み install_root を解決する。アンカーが無ければ未インストールとして停止する。
  1. status を読む。STOP なら何もせず終了（報告もしない）。MIGRATION なら現行版で継続し、準備中フォルダを根拠に実行しない。RUNNING なら現行版で通常実行。
  2. current_version が指す版フォルダを確定する（`activated_at` が null の版は未有効化として扱わない）。
  3. 現行版の `spec.yaml`（scope）→ `environments.yaml` / `services.yaml` → `projects/<slug>.yaml` の順に読む。
  4. プロジェクトの allow-list（環境・経路）と bind（サービス）と各タスクの access ピンを確定する。定義に無い環境・経路・サービスは使用禁止。
  5. runtime のスロット／キュー状態を確認する（枠が取れない・プロジェクト一時停止中なら開始せず、復旧手順に従う）。
  6. プロジェクト固有の入口へ進む。
- 出力： 確定した「現行版 × プロジェクト定義 × access ピン」の実行コンテキスト。サブエージェントは親のコンテキストを相続し、bootstrap を再実行しない。

## F2. レジストリ管理（環境／サービス／プロジェクト）

- 概要： 環境コレクションとサービス台帳はグローバルに1本。プロジェクトは使う環境を allow-list で、使うサービスを bind で宣言する。
- ID規約： 環境＝ホスト単位ID＋経路ID、サービス＝`<provider>::<persona>`、プロジェクト＝kebab-case slug、チャット＝プラットフォームのIDをそのまま。
- 入力： 環境・サービス・プロジェクトの定義変更。
- 出力： 検証（パース＋必須フィールド＋参照整合性）を通った定義ファイル。
- 制約： 認証情報の値は書かない（保管場所への参照だけ）。ペルソナ付きサービスは原則1プロジェクト専用に bind する。

## F3. intake（新規チャットの受付判定）

- 概要： 新しい作業窓ができたとき、作業開始前に必ず判定してレジストリに登録する。
- 判定（順に）：
  1. 引き継ぎか？ → 同じプロジェクトに chats 追加（`predecessor` と `role: successor` を記録）。
  2. 既存プロジェクトの新作業か？ → そのプロジェクトに chats 追加（role は design / implementation / operations / research 等）。
  3. 完全新規か？ → 先に `projects/<slug>.yaml` を作ってから登録し、作業開始。
- 出力： 登録済みの帰属（全チャットに必ず1プロジェクト）。迷ったら global に仮置きし、行き先決定後に移す。

## F4. SPEC版管理とフリップ

- 概要： 規格は版フォルダ（不変スナップショット）で管理する。変更は新版フォルダを並行作成し、承認を経て `current_version.yaml` を書き換える（フリップ）ことで有効化する。
- 入力： 変更内容、変更理由、対象範囲。
- 処理： MIGRATION 状態で新版を作成 → 現行版との差分レビュー（実データ欠落ゼロが合格条件）→ オーナー承認 → フリップ → RUNNING に戻す。
- 出力： 新現行版。ロールバックは `previous` へのフリップ1回。
- 粒度： 実行振る舞いに影響する変更＝新版。誤字・体裁のみ＝版を切らない。版は registry 全体のスナップショットで切る。

## F5. ディスパッチャ（スケジュール判定）

- 概要： 時刻・間隔・期限の判定だけをスクリプトが行い（AIトークンを消費しない）、発火したらワークフローへ渡す。
- 入力： 各タスクの `schedule` 定義（type: at / every、at / until / window / busy_minutes）、発火状態ファイル、時計。
- 処理： at は窓 [at, until] 内かつ当日未発火で発火（窓を過ぎたら skip-mark）。every は窓内かつ前回発火＋間隔経過で発火。プロジェクト単位の busy ロックで同一プロジェクトの並行実行を防ぐ。
- 出力： 発火ペイロード `{project, task, workflow, executor, delegate_chat, fired_at, reason}`（executor と delegate_chat は schemas §3.1。executor=live-browser のタスクはワークフローへ渡さず、driver cron がディスパッチャを直接駆動し delegate_chat のフルエージェントがその場で実行する（schemas §3.1 — 中継 worker にはブラウザ操作もチャット送信も無いという実測に基づく）。blocked 報告の集約は schemas §3.2）。dry_run では状態を書かない。

## F6. 実行制御（スロット／キュー）

- 概要： 資源（環境×経路×サービスアカウント等）ごとの実行枠と、タスクキューの滞留を管理する。
- スロット状態： free / busy / alert（予想超過）/ danger（+15分）/ zombie（さらに+15分）。zombie は当該資源を必要とする他タスクだけをブロックする。終了予想は定義の粗い `expected` から始め、実績が溜まったら平均に移行する。
- キュー： 通常キュー上限16（12超でアラート、16でレッドアラート、通知は遷移時1回だけ）。溢れは緊急キュー（無制限）へ。投入→開始のタイムアウト超過は報告し、当該プロジェクトを一時停止（サーキットブレーカ）する。同一プロジェクト＋同一タスク＋同一対象の重複投入は1件に統合する。
- 復旧： 全件を「投入時刻・経過・プロジェクト・タスク・推奨（実行/破棄）」で提示し、オーナー判定を受けてから再開する。
- 担い手： 専用常駐は置かない。各ランの bootstrap と定期ハートビートがついでに評価する（opportunistic）。

## F7. ドクター（監査）

- 概要： ディスパッチャ自身の停止や例外など、スロットの守備範囲外の異常を機械的に検知する。AIは検知に使わない。
- 入力： hookログの鮮度と例外、発火状態の整合、SPECのYAML／ワークフロー実在、F6の状態遷移、キューの滞留。
- 出力（段階制）： tier1（可逆で局所な手当て：zombieスロット解放＝ランの生死確認後、未来に張り付いた busy ロック掃除）は対処してから報告。tier2（基盤停止・例外連続・SPEC不整合・緊急キュー滞留・再発）は対処せず詳細報告し、オーナーの判断を仰ぐ。info は監査ログへの記録のみ。正常時は報告しない。
- 起動： 監査対象の基盤とは別系統の定期起動にする（共倒れ防止）。

## F8. インストールウィザード

- 概要： 質問に答えていく形式で稼働系を立ち上げる。選択できる項目は選択肢を出す。
- 手順：
  1. 家名の合成： ベース家名プール（`data/house-names.yaml`）を材料に、オーナーの名字等から「良い感じの響き」の家名をプロンプトで合成する（スクリプト固定ではない）。
  2. じいや・ばあやの命名（シングルトン、命名可）。飛丸は名前不変。
  3. 当主の表示名（家名＋エージェント名）を確定する（表示のみ）。
  4. ペルソナ解像度の初期値を選ぶ（零／模糊／須臾／虚空）。
  5. アバターの好み入力： プリセット（`data/avatar-presets.yaml`、32種）から選ぶか、手入力（プリセットを見本表示し「参考に入力してください。未記入の要素は良きに計らいます」と案内）。ここで保持するのは属性プロパティだけ（描画は後行）。
  6. SPEC雛形（`templates/spec/`）から初期レジストリを生成し、初版を有効化する。
- 出力： 稼働系一式（レジストリ初版、家の設定、担当者プールの有効化）。

## F9. プロジェクト生成と担当者アサイン

- 概要： ユーザーのオーダーから、概要＋スケジュール＋ワークフローを生成し、担当者をアサインする。
- アサイン： 執事／メイドは固定53ペルソナ（`data/personas.yaml`）から未アサインのものをランダムに割り当てる（オーナー命名不可、レアあり）。じいや／ばあや／飛丸が担当するプロジェクトもある。
- 性格の効き方： ペルソナの性格は挙動パラメータ（正確性／量／完成精度／納期の重み）を持つ。解像度が須臾では口調まで、虚空ではこのパラメータまで効く。
- 出力： `projects/<slug>.yaml` とプロジェクトのワークスペース。生成物は F4 の版管理に乗せる。

## F10. プロジェクトのパッケージ化とカタログ

- 概要： プロジェクト自体をパッケージ化し、カタログ（`templates/catalog/` の形式）に登録する。インストールするとカタログにセットされ、選択してプロジェクトを立ち上げられる。
- パッケージ内容： プロジェクト定義（概要・スケジュール・ワークフロー・必要環境/サービス宣言）。個人の実データ（チャットID、アカウント対応表、状態ファイル）は含めない。

## F11. ペルソナのリセマラと報告レンダリング

- リセマラ： 使用人全員の名前・ペルソナ（語尾、プロフィール、性格）・アバター属性を再生成する。ただし飛丸の名前は変わらない。再生成後の担当者が、そのプロジェクトの担当になる。
- 報告： 担当者は解像度設定に応じてペルソナの語彙で作業報告する。ウザければオフ（零）や担当者交代ができる。当主はシステムメッセージで素の口調で語る。

## F12. アバターのビジュアル化（後付け）

- 概要： インストール時点では属性プロパティだけを持つ。GUI（Space等）は後からインストールできるアドオンで、その初期処理として属性から立ち絵と顔アイコンを初めて描画する。
- 制約： 制服はクラスごとに統一（執事服／メイド服／じいや服／ばあや服／飛丸は忍者装束）。節度と清潔感のあるデザイン（ビキニ等は不可、アロハシャツは可）。年齢枠： じいや・ばあやは高齢、執事・メイドは若年〜中年、飛丸は年齢不詳、当主はナイスミドル。

## F13. リロケーション（インストール先の移設）

- 概要： 稼働系の置き場所を変える専用手順。**版の更新（F4）と同時に行わない**（変更種別を混ぜると障害時の切り分けができないため）。
- 入力： 移設先パス、オーナーの承認。
- 処理：
  1. 稼働を止める（status を STOP にする）。
  2. install_root 一式を移設先へコピーする（F14 のダンプ経由でもよい）。
  3. 移設先の中で「自分自身を指す絶対参照」だけを機械置換する。対象は棚卸しで洗い出す（恒常部品のスタブ、監査、global プロジェクトの workspace、spec.yaml のメタ情報など）。プロジェクト定義が指す**外部の作業場所**（workspace / rules_ref 等）は移設対象ではないので触らない。
  4. 検証： 全 YAML パース、current_version の指す版フォルダの実在、監査（F7）相当のチェックを通す。
  5. **アンカーの install_root を新パスへ書き換える（これが移設のコミット点）**。
  6. status を RUNNING に戻し、恒常部品の起動を確認する。旧側は検証が済むまで消さない。
- 出力： 移設完了報告（旧パス、新パス、置換した参照の一覧、検証結果）。

## F14. バックアップダンプとレジューム

- 概要： 稼働系一式を日付付きアーカイブに固める（ダンプ）と、別マシン・復旧時の再開（レジューム）。稼働系には認証情報の値が含まれない設計のため、ダンプはそのまま保管・移送できる。
- ダンプの内容： install_root 一式、アンカーの写し、manifest（作成時刻、元の install_root、家の名前、現行版と version_no、稼働状態、ファイル数、アーカイブの sha256）。
- レジュームの処理：
  1. 対象マシンに `~/.palagial/config.yaml` を書き、install_root に展開先を指定する。
  2. ダンプを展開する。展開先パスが元のパスと違う場合は F13 の参照置換を適用する。
  3. runtime のスロット占有は旧マシンの情報であり無効なので、レジューム時に初期化する（キューは内容を確認してから扱う）。
  4. 検証（全 YAML パース、現行版フォルダの実在、監査相当チェック）を通してから RUNNING で再開する。
- 出力： ダンプファイルと manifest ／ レジューム完了報告。

## F15. サービス疎通の鮮度管理

- 概要： 各サービス（接続先）が「最後に成功したのはいつか」を記録し、想定より長く成功が無いサービスを早期に検知する。ログイン停止などを開店・締切間際に発見する事故を防ぐのが目的。
- 入力： 各ランのサービス使用結果、services.yaml の台帳、対象サービスの期待使用間隔。
- 処理：
  1. サービスを実際に使って成功したランが、runtime の `service-health.yaml`（形式は data/schemas.md §9）に `last_ok` を更新する（ついで更新。専用の常駐監視は置かない）。
  2. 失敗したランは `last_error` に**種別だけ**（auth_failed / unreachable / rate_limited / unknown）を記録する。認証情報の値や本文は書かない。
  3. 期待間隔は、紐づくタスクのスケジュールから求まる最大間隔を既定とし、services.yaml に個別指定があればそれを優先する。
  4. ドクター（F7）は監査のたびに `now - last_ok > 期待間隔` のサービスを findings に挙げる。成功記録が一度も無いサービスは対象外（未使用として区別する）。
- 出力： service-health.yaml の更新、ドクター findings（該当サービスと最終成功時刻）。

## F16. 差分レビューの標準形式

- 概要： 版の移行（F4）やリロケーション（F13）の合否判定に使う、新旧フォルダ間差分の標準レポート。判定が担当者ごとの即興にならないようにする。
- 入力： 旧版フォルダ、新版フォルダ。
- 処理：
  1. ファイル単位で追加／削除／変更を数える。
  2. YAML はキー単位で比較し、追加キー・削除キー・変更キーをパスつきで列挙する。
  3. 保護カテゴリ（environments、services、各プロジェクトの tasks / schedules / access）は「不変」か「変更あり（理由つき）」を明示する。保護カテゴリの削除キーは、移行先の spec.yaml の change_reason に理由が書かれていない限り不合格とする。
  4. 判定欄に `data_loss: none` または欠落の詳細を記す。
- 出力： 差分レビューレポート（形式は data/schemas.md §10）。F4 のフリップ承認はこのレポートを根拠とする。

## F17. アンインストール（撤去）

> **先行公開版（v0.2.0）では無効化**： 本機能は仕様のみで未検証のため、参考仕様として残しますが、インストール／運用の対象外です。有効化は将来の版で行います。

- 概要： インスタンスの正式な撤去手順。オーナーの明示指示がある場合にのみ実行する。
- 入力： オーナーの撤去指示、最終ダンプを残すかどうかの選択。
- 処理：
  1. status を STOP にし、実行中ランが捌けるのを待つ（スロット確認）。
  2. 選択されていれば最終ダンプ（F14）を取る。
  3. 恒常部品（cron スタブ、hook 等）を、SPEC の登録（global プロジェクト等）から一覧化して提示し、登録解除する。
  4. **アンカー `~/.palagial/config.yaml` を削除する（これが撤去のコミット点。以後、そのマシンでは「未インストール」として扱われる）**。
  5. install_root はオーナーの選択で削除するか、アーカイブとして残す。ダンプは指示が無い限り消さない。
- 出力： 撤去報告（解除した恒常部品の一覧、ダンプの有無と場所、残したもの・消したもの）。

## F18. プロジェクトの終了手順

- 概要： プロジェクトを作る手順（F9）に対応する、閉じる手順。完了したプロジェクトが active のまま残り続けるのを防ぐ。
- 入力： 終了の判断（目的達成、またはオーナーの決定）。
- 処理：
  1. スケジュールを止める（スケジューラ側が時刻・本文の正本なので、そちらの登録を無効化／削除し、ID を記録する）。
  2. プロジェクトの status を closed にする。これは版管理された定義の変更なので、F4 の手順（新版フォルダ＋差分レビュー＋フリップ）で行う。差分は status と本手順の記録のみであることを F16 レポートで明示する。
  3. 担当者のアサインを解放する（そのペルソナは他のプロジェクトで再利用できる）。
  4. チャットの紐づけを外す（チャット自体と履歴は消さない）。
  5. プロジェクトの実ファイル（workspace 配下の成果物）はオーナーのものなので消さない。レジストリ側の参照だけを閉じる。
  6. カタログ（F10）に登録されたプロジェクトなら deprecated を付ける。
- 出力： 終了報告（止めたスケジュールの一覧、解放した担当者、閉じた版）。

## F19. 状態スナップショット出力

- 概要： 家の現在状態を1つの読み取り専用ドキュメントにまとめる出力。GUI（将来のアドオン）が読む読みモデルの正とする。
- 入力： アンカー、house.yaml、現行版一式、runtime の状態、service-health（F15）、ドクターの直近結果。
- 処理： 要求時または定期に、形式（data/schemas.md §11）で `runtime/snapshot.json` を生成する。生成は読み取りのみで、稼働系の状態を変えない。
- プロジェクト⇄チャット対応： projects には chats（対応表用の読みモデル）を含める。同じデータから、人間が読むチャットマップ台帳（Markdown）を副産物として生成してよい。状態は「プロジェクトの status／インスタンスの state／最終活動」の3層で表し、1つのラベルに潰さない。
- 出力： snapshot.json（生成時刻、家、現行版と状態、プロジェクト一覧と担当、runtime 要約、サービス鮮度要約、直近の監査結果）。

## F20. ハウスレポート（オーナー向け定期報告）

- 概要： オーナー向けに、家の活動を要約して届ける定期報告。機械向けのドクターログ（F7）とは別に、人に読ませるための層を持つ。
- 入力： 対象期間のドクターログ、runtime の状態、期間内の SPEC 変更（フリップ・終了・アサイン変更）、サービス鮮度（F15）。
- 処理：
  1. 既定は週次。期間内のプロジェクト活動（ラン回数と特記事項）、インシデントと監査 findings の要約、サービス鮮度のアラート、今後の予定（スケジュールの見どころ）、使用人のアサイン変更を集める。
  2. 家のペルソナ解像度でレンダリングして届ける。内容の完全性は解像度で変えない（変えるのは見せ方だけ）。
- 出力： オーナーの通常の連絡先への報告文。

## F21. ログ標準（統一ログ）

- 概要： コンポーネントごとの統一ログを `<install_root>/Logs/` に置き、エラーの中身を履歴として残す（状態ファイルは現在値、ログは履歴と中身、という分担）。
- 入力： 各コンポーネントのイベント（発火・監査結果・サービスエラー等）。
- 処理： 共通ヘルパーが JSON Lines で追記し、サイズ上限でローテーションする（1MB／4世代／90日）。各行に project / task / service 等の識別子を持たせ、プロジェクト別の見方は抽出で作る。認証情報の値は記録しない。
- 出力： `Logs/<component>.log`（＋世代ファイル）。形式の詳細は schemas §13。
- 拡張： 将来の拡張アプリは同じ規格で `Logs/<app-id>.log` を追加できる。ログはダンプ対象外（F14 §8）、アーカイブのみ。

## F22. 定期インスタンスチャットとプロジェクトスコープ・スキル

- 概要： プロジェクトが「期間ごとに新しいチャットを立てる」運用（例： 毎週の礼拝準備）を持つ場合、その型を宣言できる。チャット名は基準日で決まる日付サフィックスを持ち、期間が終われば終了扱いにする。
- チャットテンプレート： プロジェクト定義に chat_template（名前パターン・周期・基準日・サフィックス形式・作成タイミング・終了規則）を書く。当日に作る場合は当日の日付を使う（翌日分を先行して作らない）。終了は削除ではなくアーカイブ（履歴は残す）。
- プロジェクトスコープ・スキル： プロジェクト専用のスキル（手順書）をプロジェクト定義から参照できる。そのスキルは当該プロジェクトのチャットでのみ使用し、他プロジェクトでは使わない。スキルの実体はホスト環境のスキル置き場に置く。
- 形式の詳細は schemas §14。

## F23. ぱらぎストレージ（成果物ストレージ構成）

- 概要： プロジェクトの成果物（バッチ）を格納する場所の構成を、インスタンスやバックエンドを問わず共通化する。名前は「PaLaGial Storage」の愛称として「ぱらぎストレージ」と呼ぶ。
- 構成： `<ストレージルート>/PaLaGial/<project-id>/<yyyymmdd_hhmmss>_<sidechat-name>/<自由>`。project-id は SPEC のプロジェクト ID、タイムスタンプは格納した日時のローカルタイム、sidechat-name は成果物を出したサイドチャットの名前。最下層の使い方はプロジェクトごとに自由とし、仕様では固定しない。
- ストレージルートの解決： インスタンスが事前に決めたルート（house.yaml の `storage.root` に記録）があればそれを使う。無ければデフォルト `workspace/Storage/`。バックエンドは問わない（ローカルファイルシステム、Google Drive、iCloud、OneDrive、SFTP、WebDAV 等、コネクタやマウントで到達できるもの）。共通仕様なのはルート配下の構成だけである。
- 綴り： フォルダ名のセグメントはパッケージ名と同一の `PaLaGial` に統一する（`PaLaGiAl` のような表記ゆれを作らない）。
- 形式の詳細は schemas §15。

## F24. ぱらぎメモリ（メモリの層分けとプロジェクト別分離）

- 概要： エージェントの長期メモリを「コア（家全体の最小限）」と「プロジェクトメモリ（プロジェクト毎）」に層分けし、全チャットへ一律に渡る文脈を最小化する。狙いは、注入トークンの固定費削減と、記憶混在による文脈混濁・誤帰属の回避。名前は「ぱらぎメモリ」と呼ぶ。
- 層： (1) コアメモリ＝当主の呼び方・本人情報、絶対ルール、全域の運用ルール、プロジェクト一覧と各プロジェクトメモリへのポインタのみ。(2) プロジェクトメモリ＝プロジェクト定義に記録された `memory_file`（1プロジェクト1ファイル）。そのプロジェクトのチャットが作業開始時に読みに行く（pull）。(3) チャットローカルの一時メモはホスト環境の仕組みに委ね、本仕様の対象外。
- プロジェクト識別コード： `code` = プロジェクトID の sha256 先頭8桁（16進小文字）。決定論的で誰でも再計算でき、プロジェクト定義に記録する。
- 項目メタ： プロジェクトメモリの各項目は見出し直下にメタ行 `<!-- pm: projs=<code>[,<code>...] [Shared] [Expire_YYYYMMDD] -->` を持つ。projs は所有プロジェクトの全コード。2件以上なら Shared を明示し、項目は各所有先ファイルへ同一内容で複製する。Expire_YYYYMMDD は期限切れで削除候補になる事前承認タグ（監査が検出、所有チャットが削除または更新）。
- 再移動規則： コア側に紛れ込んだ項目がメタを持ち、projs に global のコードを含まない場合、それは誤配置であり、記載先プロジェクトへ複製してコアから削除する（機械的に判定可能）。メタのない項目は内容で判断する。
- 書き込み規則： 新しい学びは原則として所有プロジェクトのメモリへ書く。コアへの追加は家全体のルールに限る。
- 移行手順（導入時）： (1) 仕様とコードを確定する。(2) 全プロジェクト（休眠含む）へ通達し、各プロジェクトがコアから自関係分をメタ付きで自ファイルへ抽出（複製）し、完了を家の窓口へ報告する。(3) 全プロジェクト完了後、窓口が被覆表（コアの全節が コア／取得済み／台帳行き のいずれかに入ること）を確認し、移行前コアを F23 ストレージへバックアップしてから、コアだけを残して削除する。
- 形式の詳細は schemas §16。

## F25. 人物・グループメモリの再編（人物マップとプロジェクト別キャッシュ）

- 概要： F24 で対象外とした人物・グループ台帳を再編する。グループはプロジェクト別に分割し、人物は関係性タグ付きの「人物マップ」を正本として、プロジェクト毎の「人物キャッシュ」を通常の読み先にする二層にする。狙いは F24 と同じく文脈混濁の回避だが、人物はプロジェクト横断が本質であるため、プロジェクト別に割るのではなく「正本＋キャッシュ」で扱う。
- グループの分割： 単一プロジェクトに属するグループは、そのプロジェクトのメモリ領域へ移す。複数プロジェクトにまたがるグループは主所有プロジェクトを1つ決めてそこが持ち、他のプロジェクトはポインタで参照する。
- 人物マップ： 人物の正本。人物ファイル（1人1ファイル）の集合と、機械可読な登録簿（人物ごとのタグと所属キャッシュの一覧）からなる。各人物には関係性タグを付ける。
- 関係性タグ： 近さと経路を表す固定語彙（本人／家族／親戚／関係者／リアル友達／ネット友達／リアル赤の他人／ツイッター知人／ツイッター友達／ツイッター他人／Facebook知人／Facebook友達／Facebook他人）。1人に複数付けられる。語彙の追加は仕様改訂で行う。分類の最終判断は当主が行う。
- 本人とペルソナ： 当主本人は「本人」タグを持つ単一のエントリとする。本人のペルソナ（活動時期や場面ごとの別ハンドル等）は別人として立てず、本人の属性としてそのエントリに記録する。
- 人物キャッシュ： プロジェクト毎に、そのプロジェクトに関係する人物ファイルの複製を持つ。通常、そのプロジェクトのチャットが読むのは自キャッシュだけである。本人（当主）は全プロジェクトのキャッシュに必ず含める。人物がキャッシュに入るのは、そのプロジェクトの仕事に登場したとき、または手動で追加されたとき。
- 同期： 正本は常に人物マップ。プロジェクト側で得た人物についての学びはマップへ書き戻し、自キャッシュにも反映する。他プロジェクトのキャッシュは次回の pull（作業開始時）で追いつく。キャッシュとマップが食い違う場合はマップが勝つ。キャッシュは登録簿から機械的に生成できる生成物として扱い、手編集しない。
- 移行手順（導入時）： (1) 仕様を確定する。(2) 全人物・全グループを棚卸しし、タグ付けとグループ帰属の草案を作り、当主が分類を確定する。(3) グループを分割し、人物マップと各プロジェクトのキャッシュを構築する。(4) 未タグ・未帰属がゼロであることと、全キャッシュに本人が含まれることを検証してから切り替える。
- 形式の詳細は schemas §17。
